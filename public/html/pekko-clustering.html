Architecture Decision Record Status: Proposed

Pekko Cluster Peer Discovery Mechanism

Evaluating Kubernetes API vs Hazelcast for node discovery in distributed Pekko applications.

TL;DR

We are migrating our monolithic service to a clustered Apache Pekko architecture to handle stateful websockets. The nodes need to discover each other to form a cluster.

Recommendation: Proceed with the Kubernetes API approach. Since our infrastructure is strictly bound to Kubernetes and we do not span multiple datacenters, introducing Hazelcast adds unnecessary architectural complexity and memory overhead. K8s API provides a native, zero-infrastructure solution leveraging our existing control plane.

Deep Dive Comparison

Option A: Kubernetes API (Native)

Nodes query the Kubernetes API server directly to find the IP addresses of other pods matching a specific label selector.

Zero Extra Infra Fast Discovery Cloud Native K8s Vendor Lock-in Requires RBAC config
How it works (Startup Flow)
1
Pod Starts: Pekko node boots up and checks `application.conf`.
2
API Query: Node queries `https://kubernetes.default.svc` for pods with label `app=my-service`.
3
Resolution: API server returns a list of Pod IPs.
4
Join: Node selects the lowest IP to send a Join Request, forming the cluster.
application.conf
rbac.yaml
pekko.management {
  cluster.bootstrap {
    contact-point-discovery {
      # Use K8s API for discovery
      discovery-method = kubernetes-api

      # The label selector to find other pods
      pod-label-selector = "app.kubernetes.io/name=my-service"

      required-contact-point-nr = 2
    }
  }
}
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
---
# Bind role to default service account
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
roleRef:
  kind: Role
  name: pod-reader

Option B: Hazelcast (External Registry)

Nodes use Hazelcast IMDG (In-Memory Data Grid) to register themselves and discover peers, forming a ring.

Platform Agnostic Cross-DC Support Dev-friendly (Multicast) Heavy JVM Dependency Memory Overhead
How it works (Startup Flow)
1
Hazelcast Init: Embedded Hazelcast instance starts within the Pekko JVM.
2
Grid Join: Hazelcast instances discover each other (via Multicast, TCP, or cloud-specific modules) and form a grid.
3
Registry Read: Pekko queries the local Hazelcast grid state to find IP addresses of other Pekko members.
4
Join: Node sends Join Request to the lowest IP to form the cluster.
application.conf
hazelcast.xml
pekko.discovery {
  method = hazelcast
  hazelcast {
    config-file = "hazelcast.xml"
  }
}

pekko.management {
  cluster.bootstrap.contact-point-discovery {
    discovery-method = hazelcast
  }
}
<hazelcast>
  <network>
    <port auto-increment="true">5701</port>
    <join>
      <!-- Use Multicast for local dev -->
      <multicast enabled="true"/>
      <!-- Or TCP-IP for prod -->
      <tcp-ip enabled="false">
        <member-list>
          <member>machine1</member>
        </member-list>
      </tcp-ip>
    </join>
  </network>
</hazelcast>

Decision Matrix

Criteria Kubernetes API Hazelcast Winner
Infrastructure Dependencies Relies on K8s API server (already exists) Self-contained but requires Hazelcast jar overhead Kubernetes API
Local Development Harder. Requires minikube or config overrides Easy. Just works via multicast on localhost Hazelcast
Security / Auth Requires specific Kubernetes RBAC roles Requires configuring Hazelcast network security Tie
Multi-DC / Hybrid Cloud Impossible/Complex (unless using K8s Federation) Native support via Hazelcast WAN replication Hazelcast
